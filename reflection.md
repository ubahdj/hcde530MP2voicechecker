# Reflection — VoiceCheck

## What did you build?

I built a web application called VoiceCheck. VoiceCheck makes sure that the voices of low-literacy and non-English speakers aren't filtered when they are communicating with public health evaluators. It takes qualitative evaluation notes as input and returns a set of flagged passages where participant voice appears to have been paraphrased into academic language. The application can take a PDF, Word doc, or text file as input, and the output is a structured report. Between input and output is a review workflow: flagged passages are highlighted in the document, each flag appears in a side panel with a severity label and a plain-language explanation, the evaluator enters the original participant quote for comparison, and accepts or dismisses each flag before exporting. The flagging logic is a prompted LLM — the Claude API receives the document text and a prompt defining six specific linguistic patterns, and returns flagged passages with labels and explanations.

## What decisions did you make?

The platform I used to build VoiceCheck was Lovable. I chose Lovable over Cursor because the core product is interface-driven — uploading, reviewing flags, accepting or dismissing, and exporting — rather than computation-heavy, and Lovable is better suited to building that kind of workflow quickly. The most consequential decision was choosing the Design track over the Research track. My original declaration described a Research product, but the tool I had in mind required an evaluator to sit with each flag and make a judgment call. Professor Brock caught the contradiction, and I resolved it by switching tracks and rewriting the rationale. For scope, I decided to focus on six concrete flagging patterns rather than attempting to catch every possible form of voice loss — that kept the tool testable and the LLM prompt precise. I also chose a prompted LLM over custom NLP because the six patterns are contextually subtle and rule-based detection would miss most of them. The six patterns — first-person language shifted to third-person, hesitation flattened into declarative claims, emotional language replaced with clinical terms, specific details generalized, emotion removed and replaced with neutral framing, and culturally specific phrasing standardized away — were defined before building and became both the test cases and the LLM prompt instructions.

## What would you do differently?

The first thing I would change is the export report. Right now it shows the flagged passage and the participant quote the evaluator typed in, but it does not show a suggested rewrite. A more useful report would show the flagged passage, the original participant quote, and a suggested revision that restores the voice — so the evaluator leaves with something actionable rather than just a list of problems to fix on their own. Due to credit limits, I was not able to build this feature out fully. The second thing I would change is the side-by-side view. It was added late as an iteration rather than built from the start, but it is the most important feature in the tool because the comparison between what was written and what was said is the entire point of VoiceCheck. Building it first would have shaped the rest of the interface from the beginning rather than being retrofitted in. Both of these changes point to the same underlying issue — I scoped the tool around the flagging logic when I should have scoped it around what the evaluator needs to walk away with.

## What does this work demonstrate?

This project demonstrates competency across three domains. In C1 vibecoding and rapid prototyping, it shows the ability to build and iterate a deployed application — the final version went through more than a dozen prompt iterations, including diagnosing a schema error on PDF upload and fixing a data storage bug where the participant quote wasn't being saved to the flag object at the moment of acceptance, which required identifying exactly where in the flag object the data needed to be captured. In C7 critical evaluation and professional judgment, the flagging logic was tested against a five-interview mock document and all 10 returned flags were checked manually against the source before claiming the tool worked, confirming zero false positives, including subtle catches like a family's cultural threshold for medical care being reframed as a health literacy deficit. In C8 building and deploying a complete tool, the accept, dismiss, severity badge, side-by-side panel, and PDF export workflow all reflect the specific context of a public health evaluator making judgment calls about individual passages before submitting findings to a funder or health department.
